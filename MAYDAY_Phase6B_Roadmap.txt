SECTION 2 — CURRENT WEAKNESSES (HONEST ASSESSMENT)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


The following are confirmed weaknesses, not speculation:


  W1. NO EXECUTION BACKBONE
      The model generates responses as text and displays them in chat.
      Nothing parses this output. Nothing routes it to tools.
      Nothing executes it. All model output is discarded after display.
      This is the root cause of "it's just a chatbot."


  W2. NO INTENT CLASSIFICATION
      The system does not detect whether the user wants action or conversation.
      "play a tamil song" and "what is music?" get identical handling: display text.
      Intent routing (core/intent_router.py) does not exist yet.


  W3. BROWSER CONTROL IS INCOMPLETE
      Navigation to URLs may work. Everything after that — clicking links,
      reading page content, filling forms, reacting to UI changes — does not.
      Playwright is listed as a dependency but is not wired to any runtime.


  W4. NO UI READING CAPABILITY
      The system cannot inspect what is currently displayed in a browser page.
      It cannot locate buttons, links, input fields, or dynamic elements.
      Selector-based clicking is not implemented. Layout changes break everything.


  W5. NO MULTI-STEP REASONING
      Each user prompt is handled as an isolated single-step exchange.
      The orchestrator has no loop. It cannot: try → observe result → decide next step.
      The agentic loop in core/orchestrator.py is defined but broken.


  W6. NO MEMORY OR PERSISTENCE
      Every session starts from zero. No context, no task state, no goals.
      The system cannot remember "I was playing a song" or "I failed step 2."
      runtime/memory_store.py does not exist.


  W7. NO RECOVERY LOGIC
      When a browser action fails, execution stops with an unhandled error.
      There is no retry policy, no fallback strategy, no error classification.
      Failures are permanent.


  W8. HARDCODED ABSOLUTE PATHS IN BUILD SYSTEM
      build.bat contains C:\Users\GOD\... — confirmed in audit (bug C4).
      This breaks portability. The app cannot run from a USB drive or new machine.


  W9. TOOL ROUTING RESTRICTIONS AND ERRORS
      engine.py is a stub. It has register_tools() and execute() but:
        - It does not validate action schemas
        - It does not call PermissionGate
        - It does not enforce timeouts
        - It does not verify execution actually happened
      The stub returns nothing useful. Real tool dispatch is not implemented.


  W10. FAKE EXECUTION PATTERNS (R12 VIOLATIONS PRESENT)
       bootstrap/bootstrap_ui.py uses time.sleep() to fake installation progress.
       This is a known violation that Phase 10 is tasked to fix.
       These patterns must not be replicated in Phase 06b.


  W11. SPOON-FED AUTOMATION DEPENDENCY
       Current partial browser automation requires explicit step-by-step instructions
       from the user for each action. The system cannot autonomously:
         - Decide which app/site to use for a given goal
         - Search for content
         - Click results
         - Handle UI changes or errors

SECTION 4 — TOOL ACCESS PROBLEMS (WHERE ENGINE/TOOL ROUTING IS RESTRICTED)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


These are the confirmed points where tool routing breaks or is missing:


  PROBLEM 1: ENGINE STUB HAS NO REAL DISPATCH
    runtime/engine.py currently exists as a Phase 00 stub only.
    Its execute() method has no ACTION_SCHEMA validation.
    It does not look up REQUIRED_TOOL_FOR to verify a capable tool is registered.
    It does not call PermissionGate before browser or file actions.
    It does not enforce timeouts.
    It does not call assert_real_execution() to verify anything happened.
    Status: PROTOTYPE QUALITY — must be replaced in Phase 01.


  PROBLEM 2: INTENT ROUTER DOES NOT EXIST
    core/intent_router.py is listed in the handoff as MISSING.
    Without it, all prompts enter the same code path regardless of intent.
    The R11 policy (mandatory tool families per intent type) cannot be enforced.
    Status: MISSING ENTIRELY.


  PROBLEM 3: BROWSER TOOL NOT REGISTERED IN ENGINE
    browser_automation.py does not exist.
    Even if it did, it is not registered in the engine's tool dictionary.
    The ACTION_SCHEMA entries for browser_open, browser_act, browser_close
    exist in the design but point to tools that don't exist yet.
    Status: MISSING ENTIRELY.


  PROBLEM 4: PERMISSION GATE IS INCOMPLETE
    PermissionGate for browser actions is not implemented.
    Without it, browser actions either run silently (unsafe) or fail.
    The Qt signal infrastructure for showing approval dialogs is not built.
    Status: MISSING (browser variant specifically).


  PROBLEM 5: WEB ACCESS MODULE IS GATED BUT NOT WIRED
    runtime/web_access.py (Phase 06a) provides search capability.
    Without Phase 06a being complete, the browser system has no search backend
    to call when it needs to find URLs for a goal like "play a tamil song."
    Status: NOT YET BUILT (Phase 06a dependency).


  PROBLEM 6: SUBPROCESS CALLS ARE NOT CONTAINED
    Currently, subprocess calls may be scattered or absent. The design requires
    that ALL subprocess calls go through runtime/engine.py or explicitly named
    files (server_runner.py, playwright_runner.py, bootstrap/).
    Any subprocess call outside these files will fail lint in Phase 11.
    Status: STRUCTURAL RISK — must be enforced from Phase 01 onward.

SECTION 5 — BROWSER AUTOMATION UPGRADE PLAN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


The current state is: partial navigation only, no interaction, no UI reading.
The Phase 6B target is: real controllable browser with step execution and evidence.


  STEP 1 — PERSISTENT PROFILE SESSIONS (T06b.1, T06b.2)
    Use Playwright's persistent context (not incognito).
    Profile stored at: MAYDAY_ROOT/runtime/browser_profile/
    Cookies, local storage, and login sessions survive across runs.
    Chromium launched with --disable-blink-features=AutomationControlled.
    Session registry tracks active sessions by UUID.
    Each session holds one or more Page objects.


  STEP 2 — GATED ACTION EXECUTION (T06b.3, T06b.5)
    Every browser action MUST go through PermissionGate before execution.
    browser_open: shows URL to user, requires Approve or Cancel.
    browser_act: shows FULL step list preview before any step runs.
    User can cancel mid-sequence — cancellation flag checked before each step.
    In automated tests: MAYDAY_AUTO_APPROVE_BROWSER=1 enables non-interactive runs.


  STEP 3 — STEP TYPES SUPPORTED IN PHASE 6B (browser_act)
    The following action primitives are defined in ACTION_SCHEMA:
      click      — click a CSS selector
      type       — type text into a CSS selector
      wait_for   — wait for selector to appear (with timeout)
      press      — press a keyboard key (Enter, Tab, Escape, etc.)
      navigate   — go to a new URL within the session
      screenshot — capture current page state


  STEP 4 — SCREENSHOT EVIDENCE (R10/R12 REQUIREMENT)
    Every browser_open and every browser_act step takes a screenshot.
    Screenshots saved to: MAYDAY_ROOT/logs/
    Every success return dict MUST include the screenshot path.
    assert_real_execution() in engine.py checks that the path exists and > 0 bytes.
    If screenshot is missing: execution is treated as FAILED regardless of status.


  STEP 5 — AUDIT LOG (T06b.4)
    Every browser action appended to: MAYDAY_ROOT/logs/browser_audit.jsonl
    Each line contains: timestamp, action type, target, session_id,
    screenshot path, user_approved boolean.
    Log is append-only. Never truncated. Never overwritten.


  STEP 6 — ERROR HANDLING IN BROWSER ACTIONS
    If Playwright import fails: raise immediately. Never mock.
    If page.goto returns no response: raise BrowserActionError.
    If selector not found within timeout: raise BrowserActionError with step index.
    All errors are recorded to audit log before raising.


  WHAT PHASE 6B DOES NOT YET INCLUDE (deferred):
    - Semantic UI detection (reading page visually — Section 7)
    - Dynamic selector healing (finding selectors when layout changes — Section 7)
    - Autonomous site selection (choosing YouTube for "play a song" — Section 8)
    - Multi-tab coordination (Section 8)
    - DOM-level content extraction for reasoning (Section 7)

SECTION 6 — ACTION ENGINE UPGRADE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


The execution engine (runtime/engine.py) must be rebuilt from its current stub
state into a full execution hub before Phase 6B can function.


  CURRENT STATE: Prototype stub. Has register_tools() and execute() signatures
  but no real dispatch, no validation, no timeout, no verification.


  TARGET STATE AFTER PHASE 01 (prerequisite for 6B):


    ACTION_SCHEMA VALIDATION
      Every action received by engine.execute() is validated against
      ACTION_SCHEMA before dispatch. Missing required fields → error.
      Unknown action types → error. No silent failures.


    PERMISSION GATE ENFORCEMENT
      Before any browser or file write action, engine calls PermissionGate.
      If gate returns denied or cancelled, execution stops cleanly.
      No action bypasses the gate.


    TOOL LOOKUP AND DISPATCH
      engine.execute() looks up REQUIRED_TOOL_FOR[action_name].
      If the required tool is not registered: raises ToolNotRegisteredError.
      Calls tool.execute(parameters) via ThreadPoolExecutor (max 1 worker).


    TIMEOUT ENFORCEMENT
      Default timeout: 30 seconds per tool call.
      Override for browser_act: 120 seconds.
      Override for server_launch: 60 seconds.
      On timeout: ToolTimeoutError raised. Tool process cleaned up.


    REAL-EXECUTION VERIFICATION (R10/R12)
      assert_real_execution(result) called after every tool returns:
        - For file actions: verifies target path exists on disk.
        - For shell_run: verifies result contains stdout, stderr, exit_code keys.
        - For server_launch: verifies URL returns HTTP 200.
        - For browser_act: verifies at least one screenshot path exists.
      If verification fails: raises ExecutionVerificationError.
      A return dict of {'status': 'success'} alone is NEVER accepted.


    TOOL REGISTRATION (what engine will have registered by Phase 6B):
      'scaffold'       → ScaffoldEngine         (Phase 02)
      'file_write'     → FileTools              (existing)
      'file_read'      → FileTools              (existing)
      'file_patch'     → DiffEngine             (Phase 02)
      'shell_run'      → ShellRunner            (Phase 03)
      'server_launch'  → ServerRunner           (Phase 03)
      'browser_open'   → BrowserAutomation      (Phase 06b)
      'browser_act'    → BrowserAutomation      (Phase 06b)
      'browser_close'  → BrowserAutomation      (Phase 06b)
      'web_search'     → WebAccess              (Phase 06a)
      'web_fetch'      → PageFetcher            (Phase 06a)
      'remember'       → MemoryTool             (Phase 07b)
      'recall'         → MemoryTool             (Phase 07b)
      'respond'        → (no tool — direct text return)

SECTION 7 — SEMANTIC UI DETECTION PLAN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


This is the most technically complex missing piece for true autonomy.
Phase 6B as defined in the handoff uses explicit CSS selectors only.
Semantic UI detection is a LATER-PHASE capability, but the plan must exist.


  CURRENT STATE: None. Phase 6B uses only hard-coded CSS selectors passed
  in the steps list. If a page changes layout, automation fails.


  THE PROBLEM:
    "play a tamil song" requires the system to:
      1. Know YouTube is the right destination
      2. Navigate to YouTube
      3. Find the search bar (without being told its CSS selector)
      4. Type "tamil song"
      5. Find and click the first playable result
      6. Start playback
      7. Detect if playback actually began
    None of steps 2-7 are currently possible without manual instruction.


  WHAT SEMANTIC UI DETECTION WOULD PROVIDE:
    The ability to describe what to interact with in natural language
    (e.g., "the search bar", "the first video result", "the play button")
    and have the system locate it dynamically at runtime.


  APPROACH OPTIONS (in order of complexity):


    OPTION A — ACCESSIBILITY TREE PARSING (RECOMMENDED FIRST STEP)
      Playwright exposes the page's accessibility tree (ARIA roles, labels).
      A lightweight parser can match natural-language descriptions to
      accessible elements without needing CSS selectors.
      Example: "search bar" → find role=searchbox or input[type=search].
      This is prototype-quality achievable and does not require vision models.
      Reliability: medium. Works on well-structured pages (YouTube, Gmail).
      Fails on: heavily custom UIs, canvas-based apps, iframes.


    OPTION B — DOM TEXT SEARCH + HEURISTICS
      Parse page DOM for visible text matching the intent.
      "click Submit" → find button or input[type=submit] with text "Submit".
      Very brittle. Only useful for simple labeled buttons.


    OPTION C — SCREENSHOT + VISION MODEL (ADVANCED, LATER PHASE)
      Take a screenshot. Pass to a vision-capable model.
      Ask: "Where is the search bar? Return coordinates."
      Use page.mouse.click(x, y) to click at those coordinates.
      This enables interaction with any UI regardless of DOM structure.
      Requires: vision model API or local vision model.
      Gated by R5 (user must approve API calls).
      This is a Phase 09b+ capability, not Phase 6B.


  RECOMMENDED IMPLEMENTATION ORDER:
    Phase 6B:     CSS selector only (explicit, passed by model in steps)
    Phase 7-8:    Accessibility tree parser for common element types
    Phase 9+:     Screenshot + vision model with user approval gate


  SELECTOR HEALING (for layout changes):
    When a selector fails, attempt these fallback strategies in order:
      1. Re-query the accessibility tree for same role + label
      2. Wait 2 seconds and retry (handles dynamic loading)
      3. Take screenshot, log it, raise BrowserActionError with context
    Do NOT attempt more than 3 retries per selector.
    Log all healing attempts to browser_audit.jsonl.

SECTION 8 — GOAL PLANNER ARCHITECTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


The goal planner is the system that converts a high-level user statement
("play a tamil song") into a dynamic execution plan without requiring the user
to specify each step. This does NOT exist yet. Here is the architecture.


  CURRENT STATE: MISSING ENTIRELY.
  The orchestrator runs a MAX_STEPS=50 loop but has no planning capability.
  It asks the model once, gets one action back, executes it, and repeats.
  There is no goal decomposition, no sub-task creation, no plan tree.


  GOAL PLANNER — CONCEPTUAL DESIGN:


    INPUT:  A user goal expressed in natural language.
            Example: "play a tamil song on YouTube"


    PHASE 1 — GOAL DECOMPOSITION
      The model is prompted with the goal and asked to produce a plan:
      a structured list of sub-goals and the tools/actions each requires.
      This plan is stored in memory (GoalTracker + TaskMemory from Phase 07b).
      Example plan for "play a tamil song":
        Goal 1: Navigate to youtube.com           [browser_open]
        Goal 2: Search for "tamil song"           [browser_act: type + press]
        Goal 3: Click first video result          [browser_act: click]
        Goal 4: Verify playback started           [browser_act: screenshot + check]


    PHASE 2 — EXECUTION TREE
      Each sub-goal becomes a Task in TaskMemory with:
        - title
        - required action type
        - dependency list (which tasks must complete first)
        - status: pending → active → done | failed
      The orchestrator walks this tree, not a flat list.


    PHASE 3 — DYNAMIC STEP GENERATION
      At each step, the model is given:
        - The original goal
        - The current plan state (which tasks are done, active, failed)
        - The result of the last action (including screenshot)
        - The available tools
      It generates the NEXT action. Not all actions upfront.
      This allows adaptation when something unexpected happens.


    PHASE 4 — GOAL COMPLETION DETECTION
      After each action, the model is asked:
      "Has the goal been achieved? Evidence: [screenshot/result]"
      If yes: mark goal done, report success.
      If no: continue to next step.
      If stuck for 3+ steps: trigger recovery logic (Section 10).


  WHAT MAKES THIS DIFFERENT FROM SCRIPTING:
    Scripts: "click #search-bar" → fails if ID changes.
    Planner: "find the search bar" → adapts, retries, uses fallbacks.
    Scripts: fixed sequence. Planner: dynamic tree based on observed state.
    Scripts: no recovery. Planner: knows what failed and tries alternatives.


  DEPENDENCY: Goal Planner requires:
    - Phase 01 (engine with agentic loop)
    - Phase 04 (orchestrator loop + intent router)
    - Phase 06b (browser automation actions)
    - Phase 07b (memory to persist goal state across steps)

SECTION 9 — MEMORY AND TASK PERSISTENCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


Memory is required for Phase 6B autonomous execution to function.
Without memory, the system cannot track multi-step task state.
Phase 07b defines the memory architecture. Summary for this roadmap:


  CURRENT STATE: No persistence of any kind. Session resets on close.


  THREE-TIER MEMORY MODEL (Phase 07b):


    SHORT-TERM MEMORY
      Scope: Current session only.
      Storage: SQLite table short_term(session_id, role, content, ts)
      Purpose: Conversation context, action results, current step progress.
      Auto-promotion: When row count > 30, oldest rows summarized → mid-term.
      Phase 6B use: Tracks each browser step result within a session.


    MID-TERM MEMORY
      Scope: Survives session end for days/weeks.
      Storage: SQLite table mid_term(session_id, summary, source_ids, ts)
      Purpose: Compressed summaries of recent sessions.
      Phase 6B use: "I was in the middle of sending a WhatsApp message" on resume.


    LONG-TERM MEMORY
      Scope: Permanent (user-managed).
      Storage: SQLite table long_term(key, value, embedding, ts, decay)
      Purpose: Facts, preferences, learned behaviors.
      Retrieval: Cosine similarity on embeddings if available; LIKE fallback.
      Phase 6B use: "User prefers YouTube for music" stored as long-term fact.


  TASK MEMORY (Phase 07b TaskMemory + GoalTracker):
      tasks table: (id, goal_id, title, status, deps, created, updated)
      goals table: (id, title, status, parent_id, created, updated)
      resume_unfinished(): On startup, loads tasks left in 'active' state.
      Phase 6B use: If "play tamil song" was interrupted, system can resume.


  CONTEXT COMPRESSOR (Phase 07b ContextCompressor):
      Calls local model to summarize old turns into <= 300 tokens.
      Never calls external APIs without user approval (R5).
      Feeds summary into long-term memory as session facts.


  MEMORY STORAGE PATH (portable):
      MAYDAY_ROOT/runtime/memory_store/memory.db
      Self-created on first use. Never fails if missing — auto-heals.

SECTION 10 — RECOVERY AND RETRY LOGIC
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


Recovery logic is what separates a real operator from a brittle script.
CURRENT STATE: None. Any failure stops execution permanently.


  RECOVERY MUST BE BUILT AT THREE LEVELS:


  LEVEL 1 — ACTION LEVEL RETRY (within a single step)
    When a browser_act step fails (selector not found, timeout):
      Attempt 1: Wait 2 seconds, retry same action.
      Attempt 2: Try accessibility tree lookup as alternative selector.
      Attempt 3: Take screenshot, log failure, raise BrowserActionError.
    Maximum 3 attempts per action. Never infinite loop.
    All attempts logged to browser_audit.jsonl with timestamps.
    Emergency protocol E4 applies: after 3 identical failures → LOOP_DETECTED.


  LEVEL 2 — TASK LEVEL RECOVERY (within a goal)
    When a task fails after all action-level retries are exhausted:
      Option A: Ask model to generate an alternative approach for same task.
        Example: "clicking #search-bar failed → try pressing Ctrl+L instead"
      Option B: Mark task as FAILED, check if goal can still be achieved.
        Example: "search step failed → goal cannot continue → report to user"
      Option C: Request user intervention with specific context.
        Output: "RECOVERY_NEEDED: Step 'search for tamil song' failed after
                 3 attempts. Screenshot attached. Please advise."
    Maximum alternative attempts: 2 per task before escalating to user.


  LEVEL 3 — GOAL LEVEL RECOVERY (full execution failure)
    When a goal cannot complete due to cascading failures:
      Save current goal state to memory (task statuses, last screenshot).
      Report to user with full execution trace.
      Offer: retry from last successful step, abort, or pause for later.
      Do NOT silently mark goal as done.


  TIMEOUT RECOVERY:
    browser_act timeout (120s): close page, take final screenshot, raise.
    Local model timeout (90s): output API_FALLBACK_REQUEST. Wait for user. (R5)
    Server launch timeout (60s): kill process, report port, raise ServerStartError.


  WHAT RECOVERY DOES NOT DO:
    - Bypass PermissionGate (recovery still requires user approval for browser)
    - Auto-escalate to external APIs (always user-gated per R5)
    - Silently swallow errors and report success
    - Retry more than 3 times at any single level

SECTION 11 — PERMISSION AND SAFETY LAYER
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


Every browser action MUST be user-gated. This is non-negotiable.


  PERMISSION GATE DESIGN:


    For browser_open (URL navigation):
      Show dialog: "MAYDAY wants to open [URL]. Approve?"
      User sees URL before browser opens.
      Approve → proceed. Cancel → return {'status': 'cancelled'}.


    For browser_act (step sequence):
      Show dialog: Preview of ALL steps before ANY execute.
      Example display:
        Step 1: Type "tamil song" into search bar
        Step 2: Press Enter
        Step 3: Click first result
        Step 4: Take screenshot
      User sees full plan. Can approve or cancel entire sequence.
      Mid-sequence cancellation: cancellation flag checked before each step.


    For headless/test execution:
      MAYDAY_AUTO_APPROVE_BROWSER=1 env var enables non-interactive mode.
      This env var is NEVER set in production code paths.
      Only set in test environment (tests/test_browser_automation.py).


    Audit record:
      Every gate decision (approved/denied/cancelled) written to browser_audit.jsonl.
      user_approved: bool field in every audit record.


  WHAT THE PERMISSION GATE DOES NOT DO:
    - Auto-approve any action (even "safe" ones like example.com)
    - Run in silent mode by default
    - Remember previous approvals permanently (each session requires fresh approval)
    - Allow more than the previewed steps to execute


  SAFETY BOUNDARIES (must enforce even in autonomous mode):
    - Credentials: system must never fill password fields without explicit user step
    - Payments: any step targeting payment forms → escalate to user, never auto-fill
    - Destructive actions (delete, submit, confirm): always require explicit approval
    - File downloads initiated by browser: intercepted, logged, user notified

SECTION 12 — MULTI-MODEL ROUTING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


  CURRENT STATE:
    model/loader.py exists (singleton, L1 fixed).
    No routing logic. Single model only. No fallback.
    API manager (Phase 05) provides provider clients but is not yet wired.


  TARGET ROUTING ARCHITECTURE:


    PRIMARY: Local model (loaded via model/loader.py)
      Used for: intent classification, action generation, context compression.
      Timeout: 90 seconds. If exceeded → API_FALLBACK_REQUEST (R5).


    SECONDARY: External API (Claude / Gemini / OpenAI)
      Used ONLY with explicit user approval per R5.
      Never called autonomously. Never called silently.
      Gated by api_manager.py set_user_approved() — must be called by UI.


    ROUTING RULES:
      Local model available → always try local first.
      Local model times out → output API_FALLBACK_REQUEST, wait for user.
      Local model unavailable (not loaded) → output API_FALLBACK_REQUEST.
      No model at all → raise ModelNotAvailableError, inform user.


    FOR PHASE 6B SPECIFICALLY:
      Browser step generation (deciding what to click next) → local model.
      Screenshot interpretation (optional, advanced) → vision model (later phase).
      Context compression after long browser sessions → local model.


  WHAT MULTI-MODEL ROUTING IS NOT:
    - Automatic load balancing
    - Autonomous cloud escalation
    - Running multiple models in parallel
    All of these require explicit user approval or are out of scope.

SECTION 13 — LOCAL + CLOUD HYBRID EXECUTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


  CURRENT STATE: Local only. No cloud integration. API manager built in Phase 05
  but gated to require manual user approval before any call.


  HYBRID MODEL:


    LOCAL EXECUTION (default, always):
      - Model inference (local LLM via model/loader.py)
      - File operations (scaffold, write, patch)
      - Server launching (subprocess via server_runner.py)
      - Browser automation (Playwright local process)
      - Memory persistence (SQLite local file)
      - Search via SearXNG (self-hosted) or local index


    CLOUD EXECUTION (user-approved only, per R5):
      - LLM API calls (Claude / Gemini / OpenAI via api_manager.py)
      - Cloud search APIs (Brave Search, Serper)
      - Any outbound HTTP call beyond page fetching


    OFFLINE FIRST PRINCIPLE:
      The system must function completely without internet access.
      Every critical capability (model, browser, memory, file ops) runs locally.
      Cloud features are additive enhancements, not dependencies.


    FALLBACK CHAIN FOR SEARCH:
      1. SearXNG (self-hosted, local)
      2. Brave Search API (requires key, outbound)
      3. Serper API (requires key, outbound)
      Each step in chain tried only if previous fails or is unconfigured.

SECTION 15 — RUNTIME PIPELINE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


How a "play a tamil song" goal flows through the fully built system:


  USER INPUT: "play a tamil song"


  STEP 1 — INTENT CLASSIFICATION
    core/intent_router.py classifies → AUTOMATION family
    Required tools identified: browser_automation, playwright_runner
    is_executable_intent() → True
    Orchestrator enters agentic loop


  STEP 2 — GOAL DECOMPOSITION (future planner — Phase 9+)
    For now (Phase 6B level): model generates first action directly.
    System prompt from tool_system_prompt.py instructs model:
      "Respond ONLY with JSON. For automation intents: use browser_open first."
    Model generates:
      {"action": "browser_open", "url": "https://www.youtube.com"}


  STEP 3 — JSON PARSING
    core/json_parser.py parses model output → dict
    action_schema.validate(action) → valid


  STEP 4 — PERMISSION GATE
    engine.execute() calls PermissionGate.check_browser('open', 'youtube.com')
    Dialog shown to user: "Open youtube.com? [Approve] [Cancel]"
    User approves.


  STEP 5 — BROWSER OPEN
    BrowserAutomation.execute({'_tool_name': 'browser_open', 'url': '...'})
    PlaywrightRunner.launch_persistent(PROFILE_DIR) → BrowserContext
    SessionRegistry.create() → BrowserSession (uuid assigned)
    page.goto('https://www.youtube.com', wait_until='domcontentloaded')
    Screenshot saved → logs/browser_XXXXXX_open.png
    Audit record written → browser_audit.jsonl
    Returns: {'status': 'success', 'session_id': '...', 'screenshot': '...'}


  STEP 6 — REAL EXECUTION VERIFICATION
    engine.assert_real_execution(result)
    Checks: screenshot path exists and > 0 bytes → PASS


  STEP 7 — RESULT INJECTED INTO CONTEXT
    orchestrator appends result to messages as tool role
    Loop continues → model receives: {goal, last_result (success + screenshot)}


  STEP 8 — NEXT ACTION GENERATION
    Model sees screenshot evidence, generates:
      {"action": "browser_act", "session_id": "...", "steps": [
        {"action": "click", "selector": "input#search"},
        {"action": "type",  "selector": "input#search", "value": "tamil song"},
        {"action": "press", "key": "Enter"},
        {"action": "screenshot"}
      ]}


  STEP 9 — PERMISSION GATE FOR STEPS
    PermissionGate shows all 4 steps to user before any executes.
    User approves.


  STEP 10 — STEP EXECUTION WITH RETRY
    Each step executes. If selector fails:
      → Retry 1: wait 2s, retry same selector
      → Retry 2: accessibility tree lookup for input[type=search]
      → Retry 3: log failure, raise BrowserActionError
    Screenshot taken after each step.
    Audit record for each step.


  STEP 11 — RESULT + GOAL ASSESSMENT
    Model receives all screenshots. Evaluates: "Did search execute?"
    Generates next action: click first result → more steps.
    Loop continues until playback detected or failure threshold reached.


  STEP 12 — COMPLETION OR RECOVERY
    Success: model generates {'action': 'respond', 'text': 'Playing...'}
    Failure: recovery logic triggers (Section 10), user notified.

SECTION 19 — FAILURE CASES (LIKELY PROBLEMS AND HOW TO HANDLE THEM)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


  F1. PLAYWRIGHT NOT INSTALLED
      Symptom: browser_automation.py raises ImportError on import.
      Correct behavior: Raise immediately. Log clear message. Never mock.
      Prevention: build.bat must call "playwright install chromium" after venv setup.
      Test: test_browser_automation.py uses pytest.importorskip.
      Resolution path: Phase 10 (self-heal bootstrap) adds playwright install step.


  F2. CHROMIUM NOT FOUND AFTER PLAYWRIGHT INSTALL
      Symptom: playwright.sync_api.sync_playwright() context manager fails.
      Correct behavior: Raise BrowserNotAvailableError. Output NEW_DEP_REQUEST.
      Do NOT attempt to auto-download chromium silently.


  F3. SELECTOR NOT FOUND ON PAGE
      Symptom: page.click('input#search') raises TimeoutError.
      Correct behavior: 3-attempt retry with fallback selectors. Then raise.
      Log: all attempts to browser_audit.jsonl.
      Do NOT silently skip steps or mark them successful.


  F4. PAGE LAYOUT CHANGED (YouTube/Gmail redesign)
      Symptom: Hard-coded selectors stop working after site update.
      Short-term: Accessibility tree fallback (aria-label, role queries).
      Long-term: Vision model selector generation (future phase).
      Do NOT hardcode new selectors in the codebase — they will break again.


  F5. LOCAL MODEL TIMEOUT DURING STEP GENERATION
      Symptom: Local model takes > 90s to generate next action.
      Correct behavior: Pause execution. Output: "API_FALLBACK_REQUEST: local
      model timed out generating browser step. Approve cloud fallback? (Y/N)"
      Wait for user. Do NOT auto-escalate.


  F6. PERMISSION GATE BLOCKS IN NON-INTERACTIVE RUNS
      Symptom: Browser action hangs waiting for Qt dialog in headless tests.
      Correct behavior: Tests must set MAYDAY_AUTO_APPROVE_BROWSER=1.
      Production: Never set this env var. Gate remains active.


  F7. MEMORY STORE CORRUPTED OR MISSING
      Symptom: SQLite file exists but tables are missing or schema changed.
      Correct behavior: MemoryStore.connect() runs migrations, creates tables.
      Do NOT crash on missing tables. Auto-heal schema on connect.


  F8. INTENT ROUTER MISCLASSIFIES GOAL
      Symptom: "play a tamil song" classified as RESPOND instead of AUTOMATION.
      Correct behavior: ChatOnlyOutputError raised. Log misclassification.
      Fix: Add trigger patterns to TRIGGERS dict in intent_router.py.
      Test: test_intent_coverage.py must cover all example goals from this roadmap.


  F9. ENGINE RETURNS SUCCESS WITHOUT REAL EXECUTION (R12 VIOLATION)
      Symptom: assert_real_execution() fails — screenshot path does not exist.
      Correct behavior: Raise ExecutionVerificationError. Do NOT return success.
      This is the most critical failure type — it means the system is lying.


  F10. BUILD.BAT FAILS AFTER FOLDER MOVE (PORTABILITY VIOLATION)
       Symptom: Hardcoded path C:\... fails on new machine or drive.
       Correct behavior: All paths in build.bat use %~dp0 anchoring.
       Detection: grep -r "C:\\" build.bat → must return zero matches.
       This was bug C4 in audit — Phase 00 must fix it completely.

SECTION 20 — WHAT MAKES THIS DIFFERENT FROM SIMPLE AUTOMATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


Simple automation (macros, RPA scripts) executes a rigid fixed sequence.
M.A.Y.D.A.Y Phase 6B targets semi-autonomous execution. The differences:


  SIMPLE AUTOMATION                   M.A.Y.D.A.Y PHASE 6B
  ─────────────────────────────────   ─────────────────────────────────────
  Sequence defined by human           Sequence generated by model from goal
  Fails on any deviation              Retries with alternative strategies
  No context awareness                Screenshots inform next action
  Stateless between runs              Memory persists goal/task state
  Fixed selectors break on updates    Accessibility tree fallback
  No intent understanding             Intent router classifies goal type
  No audit trail                      Every action logged with evidence
  Chat-only output for intents        Real execution enforced (R10/R12)
  Silent failures                     All failures logged, user notified
  No permission layer                 Every browser action user-gated


  THE CORE DISTINCTION:


    Macro script approach:
      Step 1: Navigate to youtube.com
      Step 2: Click #search-input
      Step 3: Type "tamil song"
      Step 4: Click .ytd-video-renderer:first-child
      (These steps are pre-written by a human. If any element changes: failure.)


    M.A.Y.D.A.Y approach:
      Goal: "play a tamil song"
      → Model decides: YouTube is correct destination
      → Model generates: browser_open action
      → Executes, gets screenshot evidence
      → Model reads screenshot state, generates: type + search steps
      → Executes with retries if selector fails
      → Model reads results, generates: click first video
      → Verifies playback started via screenshot
      → If something fails: recovery logic generates alternative approach
      (Each step is generated dynamically based on what was observed.)


  WHAT PHASE 6B DELIVERS (HONEST SCOPE):
    Phase 6B delivers the infrastructure for semi-autonomous browser control.
    The model will still need to generate good selectors and action plans.
    Full autonomy (discovering execution paths completely without user guidance)
    is the target of Phases 07b through 09b with the goal planner.
    Phase 6B is the foundation — the browser can be controlled programmatically
    and the model can generate the steps. Full autonomy is Phase 9+.


  WHAT PREVENTS FULL AUTONOMY TODAY (honest bottlenecks):
    1. The local model may not generate reliable CSS selectors from screenshots.
    2. Dynamic pages (infinite scroll, lazy loading) require wait_for steps
       that the model must know to include.
    3. Login states, CAPTCHAs, and OAuth flows require human intervention.
    4. YouTube's layout changes frequently — selector reliability is not guaranteed.
    5. Playback detection requires either DOM inspection or visual interpretation.
    None of these are blockers for Phase 6B itself, which defines the step
    primitives. They are limitations on how well the model uses those primitives.

SECTION 21 — BOTTLENECKS AND CRITICAL PATH
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


These are the confirmed points most likely to cause delays or failures:


  BOTTLENECK 1: PHASE 00 BUGS (C1-C7)
    Severity: BLOCKING. Nothing works until these are fixed.
    The NumPy/torch ABI mismatch (C1) will crash model loading.
    The missing runtime/engine.py (C2) will crash main.py on import.
    The hardcoded build.bat path (C4) breaks portability.
    Do not proceed to any other phase until all 7 crash bugs are resolved.


  BOTTLENECK 2: LOCAL MODEL QUALITY
    The quality of autonomous execution is directly dependent on how well
    the local model generates valid JSON action sequences from goal descriptions.
    If the local model consistently generates malformed JSON or wrong selectors,
    Phase 6B will appear broken even though the infrastructure is correct.
    Mitigation: Strong system prompt (tool_system_prompt.py), few-shot examples
    in the prompt, and strict json_parser with regex fallback.


  BOTTLENECK 3: PLAYWRIGHT CHROMIUM INSTALLATION
    Playwright must be installed AND chromium must be downloaded.
    These are two separate steps. build.bat must handle both.
    On machines with restricted network access, chromium download may fail.
    All browser tests must gracefully skip if chromium is absent.


  BOTTLENECK 4: PERMISSION GATE + QT THREAD SAFETY
    PermissionGate emits a Qt signal from a worker thread (engine runs in
    ThreadPoolExecutor). Qt requires all UI operations on the main thread.
    Incorrect thread handling will cause crashes or silent hangs.
    This is a known PyQt6 complexity. Use signal/slot with QueuedConnection.


  BOTTLENECK 5: SELECTOR FRAGILITY
    CSS selectors for YouTube, Gmail, WhatsApp Web change frequently.
    The Phase 6B architecture supports step-level selectors passed by the model.
    If the local model cannot reliably generate correct selectors from page context,
    the system will require frequent correction. Accessibility tree fallback
    (Section 7, Option A) is the mitigation and should be implemented early.


  BOTTLENECK 6: MEMORY INTEGRATION TIMING
    Phase 6B works without Phase 07b memory, but multi-step goals cannot
    persist across interruptions without it. Plan to implement Phase 07b
    immediately after 06b. Running 06b without 07b means every session is
    stateless — the system will not recover from crashes or power loss.


  SAFEST SIMPLE IMPLEMENTATION PATH:
    Follow phase order exactly as defined in handoff (00 → 01 → 02 → 03 →
    04 → 05 → 06a → 06b). Do not skip phases. Do not merge phases.
    Each phase has explicit acceptance tests. Only proceed when all pass.
    This is slow but guarantees each layer is solid before building on it.
    Attempting to jump to 06b without 01-05 will result in missing dependencies
    that are extremely difficult to debug and retrofit.
